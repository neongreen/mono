🛡️ Demo 2: Sandbox Attributes (Limited Protection)

Understanding what iframe sandbox can and cannot protect against.

⚠️ Key Finding: Sandbox attributes provide security isolation but DO NOT prevent memory leaks or process sharing. Memory issues still affect the parent page.

What is Sandbox?

The sandbox attribute applies extra restrictions to iframe content. It's designed for security, not performance or memory isolation.

Without Sandbox

<iframe src="...">

Full permissions:

  • ✅ Can run scripts
  • ✅ Can access same-origin data
  • ✅ Can submit forms
  • ✅ Can open popups

With Sandbox

<iframe sandbox="">

Restricted (empty sandbox):

  • ❌ No scripts
  • ❌ No same-origin access
  • ❌ No form submission
  • ❌ No popups

Sandbox with Scripts

<iframe sandbox="allow-scripts">

Scripts enabled but restricted:

  • ✅ Can run scripts
  • ❌ Treated as cross-origin
  • ❌ No popups (unless allowed)
  • ❌ No modals (unless allowed)

Sandbox + Modals

<iframe sandbox="allow-scripts allow-modals">

More permissions:

  • ✅ Can run scripts
  • ✅ Can show modals
  • ❌ Still treated as cross-origin

Sandbox Flags Reference

Flag What it Allows Security Impact
allow-scripts JavaScript execution ⚠️ Required for interactive content
allow-same-origin Access to same-origin data 🚨 Dangerous with allow-scripts
allow-forms Form submission ✓ Usually safe
allow-popups Opening new windows ⚠️ Can be annoying
allow-modals alert, confirm, prompt ⚠️ Can interrupt user
allow-top-navigation Navigate parent page 🚨 Very dangerous

⚠️ Critical Limitation: Memory and Performance

Issue Sandbox Protects? Why/Why Not
Memory leaks ❌ NO Sandbox doesn't provide process isolation
High CPU usage ❌ NO Shares same thread as parent
Tab crashes ❌ NO Shares same browser process
Cross-site scripting ✅ YES Restricts script capabilities
Cookie theft ✅ YES Blocks same-origin access
Unauthorized forms ✅ YES Can block form submission

Testing: Sandbox Does NOT Prevent Memory Leaks

// This iframe will still leak memory despite sandbox
<iframe 
  sandbox="allow-scripts"
  srcdoc="<script>
    let leak = [];
    setInterval(() => {
      leak.push(new Array(10000).fill('data'));
    }, 100);
  </script>">
</iframe>

The memory leak in the sandboxed iframe will still affect the parent page because they share the same process and memory space.

⚠️ Dangerous Combination

// DON'T DO THIS - defeats the purpose of sandbox
<iframe sandbox="allow-scripts allow-same-origin"></iframe>

Using allow-scripts and allow-same-origin together allows the iframe to remove its own sandbox attribute, defeating security.

When to Use Sandbox

  • ✅ Use for security: Restricting capabilities of untrusted content
  • ✅ Use as defense-in-depth: Additional layer alongside other protections
  • ❌ Don't rely on for memory: Won't prevent memory leaks or performance issues
  • ❌ Don't use alone: Not sufficient for isolating buggy code

Recommended Approach

// Combine sandbox with cross-origin for both security AND isolation
<iframe 
  src="https://sandbox.yourdomain.com/preview"
  sandbox="allow-scripts"
  style="width: 100%; height: 600px;">
</iframe>

This gives you:

  • ✅ Security restrictions (from sandbox)
  • ✅ Process isolation (from cross-origin)
  • ✅ Memory protection (from cross-origin)

Browser Support

  • Sandbox attribute: All modern browsers
  • Granular flags: Most flags supported everywhere
  • Process isolation: Only with cross-origin (see Demo 3)

Conclusion

Sandbox is useful for security but not for performance/memory isolation. To protect against memory leaks and crashes, you must use cross-origin iframes. See Demo 3 for the proper solution.
