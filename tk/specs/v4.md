# tk spec v4

unified project + task model (numbers as labels)

---

## 1 Overview

tk is an event-sourced task tracker.
Every change is an immutable event; the current state is a projection.
Spec v4 defines projects as first-class entities and treats task numbers as mutable labels, not identities.

This is a **single-user hard break**. Version 4 is **not wire-compatible** with v1/v2. The upgrade is automatic on first run of the v4 binary.

---

## 2 Storage and Versioning

| item | path | notes |
|------|------|-------|
| database | `~/.tk/tk.db` | upgraded in-place; backup kept as `tk.db.v3.bak` |
| remote segments | `<remote>/v4/` | all v4 segments live here |
| segment header | `"spec_version": 4` | required; ingest rejects others |

The same remote is reused; v4 writes under a `v4/` subdirectory inside the existing remote.

On startup, the binary reads `meta.version_major`.  
If missing or `<4`, migration runs automatically.

---

## 3 Automatic Migration

When the v4 binary first runs on a v1/v2 database, it automatically performs in-place migration.

### 3.1 Safety Snapshot
1. Copy current `tk.db` to `tk.db.v3.bak`
2. Create `migrate-v4.lock` to prevent concurrent runs

### 3.2 Schema Upgrade
Adds the new tables in-place:

```sql
projects(project_uid PK, type, name, description, created_at, created_by);
project_aliases(project_uid, alias, node, added_by, PRIMARY KEY(alias,node));
tasks(task_uid PK, project_uid, created_node, title, created_at, created_by);
task_numbers(project_uid, number, task_uid);
metadata(key,value);
```

### 3.3 Backfill → v4 Events

For every legacy record:

| legacy | v4 event(s) |
|--------|-------------|
| `prefix.created` | `project.created` {type:"local",name:`<prefix>`} + `project.alias.add` {alias:`<prefix>`,node:`<this>`} |
| task record | `task.created` {task_uid,project_uid,proposed_number} + `task.number.set` {number:`<old>`} |
| `task.reprefix` | `task.relocate` {from_project_uid,to_project_uid,number_policy:{mode:"force",number:`<new>`}} |

Events are emitted in timestamp order and projected immediately.

### 3.4 Finalize
- Set `meta.version_major` = 4
- Set `config.remote_subdir` = "v4"
- Drop the lock
- Keep `tk.db.v3.bak` for rollback

---

## 4 Rollback

```bash
tk admin rollback-v4
```

Restores `tk.db.v3.bak` and resets `meta.version_major` = 3.
The v4 segments remain untouched and can be ignored.

## 5 Core Entities

### 5.1 Project

| field         | meaning |
|---------------|---------|
| project_uid   | stable ULID identifier (`prj_…`) |
| type          | `local` |
| name          | human-readable name |
| description   | text |
| created_at    | timestamp |
| created_by    | actor |

### 5.2 Project Alias

| field         | meaning |
|---------------|---------|
| alias         | short string used in CLI (tk, backend, mono, …) |
| node          | node where alias is defined |
| project_uid   | link to project |
| added_by      | actor |

Aliases are per-node and may collide freely.

### 5.3 Task

| field         | meaning |
|---------------|---------|
| task_uid      | stable ULID (`tsk_…`) — true identity |
| project_uid   | owning project |
| created_node  | origin node id |
| title         | text |
| created_by    | actor |
| created_at    | timestamp |

### 5.4 Task Number (Label)

| field         | meaning |
|---------------|---------|
| project_uid   | scope |
| number        | integer label (not unique) |
| task_uid      | target |

Multiple tasks may share the same (project_uid, number); collisions are resolved in display only.

## 6 Identifiers & Rendering

| form | meaning | example |
|------|---------|---------|
| `tsk_01J5Q…` | stable internal id | always unique |
| `foo-7` | alias + number | may refer to 1 or many tasks |
| `foo-7-abc123` | disambiguated with node hint | render when collision exists |
| owner/repo#27 | renderer for external project | GitHub example |

Display strings are derived views, never stored in events as IDs.

### 6.1 Rendering Rules

| case | display form |
|------|--------------|
| unique number | `<alias>-N` |
| collision | `<alias>-N-<node6>` |
| external (future) | `<owner>/<repo>#N` |
| raw id | `tsk_<ulid>` |

## 7 Events

| kind | essential fields | meaning |
|------|------------------|---------|
| `project.created` | `project_uid`,`type`,`name`,`description`,`created_by` | declare project |
| `project.alias.add` | `project_uid`,`alias`,`node`,`added_by` | define local alias |
| `project.alias.remove` | `project_uid`,`alias`,`node` | remove alias |
| `task.created` | `task_uid`,`project_uid`,`proposed_number?`,`created_node`,`title`,`created_by` | create task |
| `task.number.set` | `task_uid`,`project_uid`,`number`,`reason` | assign or change label |
| `task.relocate` | `from_project_uid`,`to_project_uid`,`number_policy`,`task_uid` | atomic move + renumber |
| `task.status.set`, `task.note.add`, etc. | — | unchanged from earlier spec |

All events sync across nodes symmetrically.

### 7.1 task.relocate Event

The `task.relocate` event atomically handles:
- Moving a task from one project to another
- Renumbering within the new project
- Resolving collisions via number_policy (`keep`, `auto`, `force N`, `fail`)

This is the v4 equivalent of `task.reprefix` from v1/v2, which was already atomic. The key difference is that v4 uses stable project UIDs instead of prefix strings.

---

## 8 Creation Semantics

```bash
tk new --project <selector> "title"
```

1. Resolve `<selector>` → `project_uid` via alias or explicit uid.
2. Compute `proposed_number = max(number) + 1` (best-effort, doesn't fill gaps).
3. Emit `task.created` { `task_uid`, `project_uid`, `proposed_number`, … }.
4. If later a collision is detected, emit `task.number.set` to renumber (optionally automatic).

Offline nodes may choose the same number; after sync these coexist as distinct tasks. Numbers may have gaps by design.

---

## 9 Task Editing

- `tk edit <task> <field> <value>` → emit appropriate event for field change.
- Common edits:
  - `tk edit <task> number <N>` → emit `task.number.set` event
  - `tk edit <task> title "..."` → emit `task.title.set` event
  - `tk edit <task> status <status>` → emit `task.status.set` event
- Projects may be renamed or merged without affecting task_uids.
- After a merge, numbers can be re-assigned in bulk for tidiness.

---

## 10 Task Movement

- `tk mv <task> <target> [--keep|--auto|--force N] [--on-collision fail|auto]` → emit `task.relocate` event
- Atomic operation that combines project change and renumbering
- Resolves collisions via number_policy

---

## 11 Lookups

Resolution priority:
1. Exact `task_uid`.
2. `<alias>-<number>` → resolve to tasks within that project.
3. If multiple tasks share number, show list with node hints.
4. Numeric alone → ambiguous error with suggestions.

## 13 Renderers

Renderer selects string form by type and origin.

| type | rule | example |
|------|------|---------|
| local | `<alias>-<number>` | `tk-1` |
| local collision | `<alias>-<number>-<node>` | `tk-1-def456` |
| github | `<owner>/<repo>#<number>` | `neongreen/mono#27` |
| linear | `<team_key>-<number>` | `DEV-42` |

---

## 14 Sync Behavior

- All events stored locally, then pushed under `<remote>/v4/`.
- Pull ignores any non-v4 files.
- No dual-write, no mixed-version sync.
- All events are replicated verbatim.
- Every node eventually learns every project, task, and number assignment.
- Collisions in numbers are permitted; UI renders with node hints until renumbered.

## 15 Commands

| command | semantics |
|---------|-----------|
| `tk project create <name> [desc]` | emits `project.created` |
| `tk project alias add/remove` | emits `project.alias.add/remove` |
| `tk new --project <selector> "title"` | emits `task.created` |
| `tk edit <task> number <N>` | renumber within same project (`task.number.set`) |
| `tk mv <task> <target> [--keep\|--auto\|--force N] [--on-collision fail\|auto]` | atomic move + renumber (`task.relocate`) |
| `tk ls [--project x]` | list tasks by renderer strings |
| `tk id <ref>` | shows task_uid, current render |
| `tk doctor` | health check |
| `tk events stats` | show event statistics |
| `tk conflicts numbers --project <x>` | lists label collisions |

---

## 16 Authority Model

tk core does not enforce permissions.
Any actor may emit events for any known project.
External remotes (once implemented) will apply their own authorization.

---

## 17 Guardrails

- The v4 binary refuses to ingest any segment not under `v4/` or without `"spec_version": 4`.
- `tk doctor` auto-runs post-upgrade and verifies:
  - every task has a valid project,
  - all aliases resolve,
  - reports any label collisions.

---

## 18 Diagnostics

- `tk doctor` (automatic after upgrade)
- `tk conflicts numbers --project <x>` lists label collisions
- `tk events stats` confirms event count parity with pre-migration total

## 20 Invariants

- `task_uid` is the only immutable identifier.
- Labels (number, alias) may collide and change.
- All events are append-only and idempotent.
- Any string form can be regenerated from events.

---

## 21 Summary for Implementors

- Store and sync immutable UID-based events.
- Treat numbers and aliases as mutable labels.
- Render disambiguated forms when needed.
- Allow renumber, merge freely.
- Identity = `task_uid`, not prefix-number-node.

Result: a simple distributed model that remains fully offline-safe, permits collisions and renumbering, and keeps user-facing labels pleasant and human.
